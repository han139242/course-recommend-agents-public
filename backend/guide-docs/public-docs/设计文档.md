# 架构设计与服务通信规约

本系统（"突破课程边界的人工智能专业知识点推荐智能体"）的架构核心旨在解决**数据一致性**、**在线低延迟响应**与**大模型长耗时推理**之间的物理冲突。系统划分为**前端展示层**、**在线 API 服务（Go）**与**离线数据流水线（Python）**三个可部署单元，通过 **Redis Pub/Sub** 实现在线与离线的异步解耦，通过 **Redis** 实现高速状态缓存。

### 团队技术栈约束

| 角色 | 技术栈 | 负责模块 |
|---|---|---|
| 开发 A | Go | 在线 API Server（BFF、用户状态、能力聚合、推荐引擎、图谱查询、用户能力图谱写入） |
| 开发 B | Vue 3 / JavaScript | 前端展示层（知识图谱可视化、能力雷达图、学习路径、答题交互） |
| 开发 C | Python | 离线数据流水线（爬虫、语料处理、LLM 抽取、知识图谱写入） |

## 一、全局存储与中间件规约

### 组件职责与连接权限

| 组件 | 选型 | 核心职责 | 连接权限 |
|---|---|---|---|
| 图数据库 | Neo4j | 存储知识图谱（知识点、课程、先修/依赖/包含等有向边）与用户能力图谱（`User`-`HAS_COMPETENCY`->`Competency` 关系及能力快照）。 | Go 侧：`GraphQuery` 模块只读 + `GraphWriter` goroutine 写入用户能力图谱。Python 侧：`GraphWriter` 模块写入知识图谱。**两侧写入不同数据域，禁止交叉写。** |
| 持久化库 | MySQL | 用户基础信息、JWT 凭据、行为日志落盘兜底、强一致性业务状态。 | 仅 Go API Server 的 `UserState` 模块连接。 |
| 高速缓存 | Redis | `O(1)` 状态读取。Hash 结构存储用户知识掌握度向量（`uid:{id}:kp`）与能力聚合值。 | Go API Server：`UserState`(R/W)、`Competency`(R/W)、`Recommend`(R)。 |
| 事件总线 | Redis Pub/Sub | 在线与离线异步解耦。用于跨语言拓扑变更通知。 | Python GraphWriter 发布 `topology_updates`，Go Competency 模块订阅并热更新权重矩阵。 |

## 三、Go API Server（在线服务）

该服务以**单 Go 二进制**部署，内部按 `internal/` 包划分业务模块，模块间通过函数调用通信，无需 gRPC。承载所有在线用户请求，强制要求 **P99 < 100ms**。

### 模块 1：BFF 路由层

**所在包：** `internal/bff`

核心职责：系统唯一对外 HTTP 入口，承担路由分发、JWT 鉴权中间件、限流。
- In：前端 HTTP 请求。
- Out：分发至内部业务模块（函数调用）。
- 约束：无状态，禁止执行业务逻辑或直连数据库。

### 模块 2：用户状态模块（UserState）

**所在包：** `internal/userstate`

核心职责：实时处理学习行为数据，计算并更新知识点掌握度。
**数据流：**
1. 接收 BFF 下发的行为埋点数据。
2. 计算掌握度增量（`Δ`），使用 Redis `HINCRBYFLOAT` 原子更新状态向量。
3. 定期（如每 60 秒）批量持久化 Redis 状态快照至 MySQL。
**容错约束：**
- Redis 写入成功即返回 200，若 Redis 不可用则降级为只写 MySQL 并返回 `degraded:true`。
- MySQL 批量持久化周期与 Redis 快照策略需配合，最大丢失窗口 ≤ 60s。

### 模块 3：能力聚合模块（Competency）

**所在包：** `internal/competency`

核心职责：将知识点掌握度映射为能力维度值，输出雷达图/进度条数据，并触发用户能力图谱落库。
**数据流：**
1. 接收 BFF 的画像查询请求。
2. `O(1)` 读取 Redis 获取用户掌握度向量，执行内存权重矩阵点乘，计算各能力维度值。
3. 将聚合结果缓存至 Redis 并返回给 BFF。
4. 将用户能力画像更新事件通过 Go Channel 发送至 GraphWriter Goroutine，异步写入 Neo4j。
**缓存热更新：**
- 后台 goroutine 订阅 Redis Pub/Sub `topology_updates`，更新内存中的权重矩阵（由 Python GraphWriter 发布）。
- 矩阵更新采用双缓冲策略：新矩阵完整加载后原子切换指针，更新期间请求使用旧版矩阵。
**约束：**
- 严禁在此模块执行 SQL 查询或图遍历。
- 在线返回链路目标 `P99 < 20ms`（画像维度已预压缩前提下）。

#### 能力图谱数据模型

**Neo4j 节点与边定义：**
```
(:Course {name: "计算机视觉"})
  ──[:CONTAINS]──→
(:KnowledgePoint {id: "kp_001", name: "卷积神经网络"})
  ──[:MAPS_TO {weight: 0.4}]──→
(:Competency {id: "comp_A", name: "深度学习", category: "AI核心能力"})

(:User {uid: "u_001"})
  ──[:HAS_COMPETENCY {score: 0.72, snapshot_time: "..."}]──→
(:Competency {id: "comp_A"})
```
| 节点/边 | 属性 | 数据域归属 |
|---|---|---|
| `KnowledgePoint` | id, name, canonicalName, entityType, description, chapterTitle, sourcePath, course_id | 知识图谱（Python 写入） |
| `Competency` | id, name, category | 知识图谱（Python 写入） |
| `Course` | id, name | 知识图谱（Python 写入） |
| `User` | uid | 用户能力图谱（Go 写入） |
| `MAPS_TO` 边 | weight | 知识图谱（Python 写入） |
| `HAS_COMPETENCY` 边 | score, snapshot_time | 用户能力图谱（Go 写入） |
| `CONTAINS` 边 | — | 知识图谱（Python 写入） |
| `PREREQUISITE_OF` 边 | — | 知识图谱（Python 写入） |
| `RELATED_TO` 边 | — | 知识图谱（Python 写入） |
| `SUBTOPIC_OF` 边 | — | 知识图谱（Python 写入） |
| `APPLIES_TO` 边 | — | 知识图谱（Python 写入） |

> **数值范围约定：** Redis / MySQL 中学生知识点掌握度（`mastery_score`）取值 **0-100**。Neo4j `HAS_COMPETENCY` 边的 `score` 取值 **0-1**（经权重矩阵计算后的能力维度归一化分数）。两者虽来源相关但含义不同，开发时注意区分。

**计算流程：**
1. 从 Redis 读取用户掌握度向量。
2. 内存映射矩阵（从 `MAPS_TO` 边预加载，`topology_updates` 热更新）。
3. 矩阵乘法得到每个能力维度的分数。
4. 返回前端渲染雷达图。
5. 异步写入 Neo4j（Go Channel → GraphWriter），使用 `MERGE` 幂等写入。

### 模块 4：推荐引擎模块（Recommend）

**所在包：** `internal/recommend`

核心职责：结合先修逻辑与依赖关系，突破课程边界，计算跨课程学习路径。
**数据流：**
1. 接收 BFF 的推荐请求（目标节点 + UserID）。
2. 调用 GraphQuery 模块拉取目标节点的先修闭包子图。
3. 从 Redis 批量读取用户掌握度向量。
4. 执行 DAG 拓扑排序、先修裁剪、薄弱点识别与路径评分。
5. 返回推荐结果（含推荐原因与学习顺序）。
**算法约束：**
- 拓扑排序时间复杂度 `O(V+E)`，单次子图规模上限建议 `V ≤ 500, E ≤ 2000`。
- 算法内部计算时间目标 `< 30ms`，端到端延迟（含网络 I/O）需单独压测。
- 新用户冷启动：掌握度向量初始化为全零，推荐从基础先修节点开始。

### 模块 5：图谱查询模块（GraphQuery）

**所在包：** `internal/graphquery`

核心职责：维护 Neo4j **只读**连接池，对外提供标准化的子图检索能力。
- 仅允许只读 Session，代码层面强制拒绝 `CREATE`/`MERGE`/`DELETE` 语句。
- 提供子图检索、先修闭包查询、用户能力快照查询等标准化接口。
- 整个 Go API Server 中仅此模块持有 Neo4j 只读连接池。

### 模块 6：GraphWriter Goroutine

**所在包：** `internal/graphwriter`

核心职责：异步接收用户能力画像更新指令，微批次写入 Neo4j。
**数据流：**
1. 通过 Go Channel 接收 Competency 模块发送的写指令。
2. 按批次（`N=100` 条）或时间窗口（`T=3s`）聚合。
3. 使用 `UNWIND + MERGE` 批量提交 Neo4j 事务。
4. 写入成功后可选发布 `user_graph_updated` 事件至 Redis Pub/Sub（如需进一步通知）。
**约束：**
- 仅写入用户能力图谱数据域，禁止写入知识图谱实体。
- 事务失败重试 3 次后写入本地死信日志。

### 用户认证

JWT 签发与校验集成在 Go API Server 内部：
- `POST /api/auth/login`：登录，签发 JWT（含 `uid`、`exp`）。
- `POST /api/auth/register`：注册（当前阶段不实现，学生账号由教师端统一创建）。
- BFF 中间件统一校验 JWT，提取 `uid` 注入请求上下文。

## 四、Python Offline Pipeline（离线服务）

该服务以**单 Python 进程**部署，内部按模块划分，使用 **标准库 `queue.Queue`** 进行阶段间的缓冲，跨语言拓扑变更使用 **Redis Pub/Sub**。

### 模块 1：爬虫采集模块（Crawler）

核心职责：对接 NeurIPS、CVPR 等顶会与期刊，采集论文题录、摘要与技术要点。
**数据流：**
- 定时触发（如 cron 调度或 APScheduler），抓取 HTML/PDF。
- 解析后将原始文档以 JSON 放入内部 `raw_queue`（`queue.Queue`）。

### 模块 2：语料处理模块（DocProcess）

核心职责：文本清洗、降噪、统一编码、去重；执行上下文感知的文本分片。
**数据流：**
- 从 `raw_queue` 消费。
- 执行正则清洗 + NLP 分句/分块（如 spaCy、LangChain TextSplitter）。
- 将纯文本块放入 `chunk_queue`。

### 模块 3：LLM 抽取模块（LLMExtract）

核心职责：调用大模型扫描语料，抽取知识点实体与关系三元组；执行实体消歧与归一化融合。
**数据流：**
- 从 `chunk_queue` 消费。
- 构造 Prompt 调用大模型 API，解析生成三元组 JSON。
- 将知识图谱写指令放入 `kg_queue`。
**容错约束：**
- LLM API 调用配置超时（建议 60s）与重试（最大 3 次，指数退避）。
- 配置令牌桶限流，防止费用失控。
- 解析失败的文本块记录至错误日志，不阻塞后续消费。

### 模块 4：知识图谱写入器（GraphWriter）

核心职责：消费 `kg_queue`，批量写入 Neo4j。
**数据流：**
- 从 `kg_queue` 消费。
- 按批次（`N=500` 条）或时间窗口（`T=3s`）聚合。
- 使用 `UNWIND + MERGE` 批量提交 Neo4j 事务。
- 写入成功后通过 **Redis Pub/Sub** 发布 `topology_updates`，通知 Go 端刷新权重矩阵。
**约束：**
- 仅写入知识图谱数据域，禁止写入用户能力图谱实体。
- 写入幂等（`MERGE`），避免重复。
- 事务失败记录原始命令 + 错误原因至死信日志，重试 3 次后跳过。

## 六、关键数据流转闭环

### 闭环 1：答题更新 → 刷新雷达图
```
前端                  Go API Server                    Redis          Neo4j
 │                        │                              │             │
 │─POST /learning/answers─→│                              │             │
 │                        │─ UserState: HINCRBYFLOAT ──→ Redis         │
 │                        │                              │             │
 │←── 200 OK ─────────────│                              │             │
 │                        │                              │             │
 │─GET /competency/profile→│                             │             │
 │                        │─ Competency: Redis读 + 矩阵乘 →           │
 │                        │─ 结果缓存 Redis               │             │
 │                        │─ Go Channel → GraphWriter ─────MERGE───→│
 │←── 雷达图 JSON ─────────│                              │             │
```
**延迟目标：**
- 答题提交链路（步骤 1→返回 200）：`P99 < 20ms`
- 雷达图刷新链路（步骤 2→返回 JSON）：`P99 < 20ms`
- 端到端用户体感（提交 + 刷新）：`P99 < 100ms`

### 闭环 2：用户请求推荐 → 返回学习路径
```
前端                  Go API Server                              Neo4j
 │                        │                                        │
 │─GET /recommend/path───→│                                        │
 │                        │─ Recommend → GraphQuery ──只读查询────→│
 │                        │                          ←─子图返回────│
 │                        │─ Recommend → Redis 批量读掌握度         │
 │                        │─ 拓扑排序 + 路径评分                    │
 │←── 推荐路径 JSON ───────│                                        │
```
**延迟目标：**
- 算法计算（拓扑排序+评分）：`< 30ms`
- 端到端延迟（含 Neo4j 查询 + Redis 读取）：需压测评估，建议目标 `P99 < 200ms`。

### 闭环 3：离线知识图谱构建
```
Crawler ──→ queue(raw_queue)
   │
DocProcess 消费 → queue(chunk_queue)
   │
LLMExtract 消费 → queue(kg_queue)
   │
GraphWriter 消费 → Neo4j MERGE 写入
   │
   └─→ Redis Pub/Sub topology_updates → Go Competency 热更新矩阵
```
**吞吐目标：** 容忍高延迟（分钟级），优先保证数据完整性与幂等性。

## 七、向量检索扩展预留

当前推荐主路径基于知识图谱、掌握度向量与先修关系计算，**不引入向量数据库**。若后续需支持 RAG 或语义相似课程召回：
- 新增独立向量检索服务（如 Milvus/Qdrant + Python）。
- 向量召回结果作为候选集输入推荐引擎，由图谱规则进行重排。
- 与当前图谱推荐链路并行，不耦合。

---

## 八、未来扩展路径

当用户规模增长或业务复杂度提升时，模块化设计已预留拆分接口：
| 触发条件 | 拆分动作 |
|---|---|
| 在线 QPS 显著增长 | `Recommend` 模块独立为 Recommendation Service，gRPC 通信 |
| LLM 调用量激增 | `LLMExtract` 模块独立部署，按 GPU 资源独立扩缩容 |
| 图谱写入吞吐瓶颈 | 两个 GraphWriter 可各自独立为微服务 |
| Go Channel 不满足解耦需求 | Go 侧用户能力图谱写入链路从 Go Channel 升级为 Redis Pub/Sub，实现跨进程解耦 |
