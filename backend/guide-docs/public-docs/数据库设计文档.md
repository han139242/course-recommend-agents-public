# 数据库设计文档

本文件用于配合 `设计文档.md` 与 `online-api-contract.md`，给出当前推荐系统在 Go 在线服务 + Python 离线流水线架构下的数据库设计建议。

目标：

- 支持教师端封闭建班、建教师、导入学生、导入题目。
- 支持学生答题、知识点掌握度更新、教师查看学生知识状态。
- 支持 Go 在线服务使用 Redis 做实时状态缓存，MySQL 做事务与报表落盘，Neo4j 做知识图谱与用户能力图谱。

## 一、存储分工

### MySQL

负责强一致业务数据与事务型数据：

- 用户、班级、教师、学生
- 题目、选项、题目与知识点绑定
- 学生答题记录
- 知识点掌握度快照落盘
- 教师端查询所需报表型明细

### Redis

负责实时缓存：

- 学生知识点掌握度向量：`uid:{id}:kp`
- 学生能力画像聚合值
- 热门画像结果缓存
- 可选的推荐结果短期缓存

### Neo4j

负责图结构：

- 知识图谱实体与关系
- 用户能力图谱
- 知识点到能力维度映射
- 先修 / 关联 / 子主题 / 应用场景关系
- 前沿知识域中的论文、研究主题、扩展摘要与课程知识点关联

补充说明：

- 当前仓库里已稳定落地的是课程知识图谱抽取与导入链路，前沿知识域仍处于“本体与文档先行、在线接口后补齐”的阶段。
- 因此前沿知识相关设计需要同时区分“已实现的数据落点”和“二期规划的数据落点”，避免把目标态误写成现状。

## 二、MySQL 逻辑表设计

## 1. users

统一用户表，当前只保留教师与学生两类。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | 用户主键 |
| `name` | varchar(64) | 姓名 |
| `email` | varchar(128) unique | 登录邮箱 |
| `password_hash` | varchar(255) | bcrypt 哈希 |
| `role` | varchar(16) | `teacher` / `student` |
| `title` | varchar(64) null | 教师职称 |
| `student_no` | varchar(64) null | 学号，学生专用 |
| `class_id` | bigint null | 所属班级 |
| `target` | varchar(255) default '' | 目标方向 |
| `status` | varchar(16) | `active` / `disabled` |
| `created_by` | bigint null | 创建人教师 ID |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

约束建议：

- `email` 全局唯一。
- `student_no` 对学生唯一，可加唯一索引。MySQL InnoDB 中多个 NULL 不违反唯一约束，因此教师行的 `student_no = NULL` 不受影响。
- `role = teacher` 时 `class_id` 允许为空。
- `role = student` 时 `class_id` 必填。
- `status` 字段须在登录逻辑中校验：`disabled` 状态的用户登录应返回错误。当前阶段不实现教师端“禁用用户”API，`status` 仅预留。

## 2. classrooms

班级表。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | 班级主键 |
| `name` | varchar(128) | 班级名称 |
| `grade` | varchar(64) null | 学期 / 年级 |
| `teacher_id` | bigint | 班级负责人教师 ID |
| `status` | varchar(16) | `active` / `archived` |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

约束建议：

- `teacher_id` 关联 `users.id`。
- 同一教师下班级名称建议唯一。

说明：

- API 层 `Classroom` 模型中的 `studentCount` 字段不在此表冗余，由查询时 `JOIN users` 表 `COUNT` 聚合得出。
- 班级查询作用域：教师只能查看和管理自己创建的班级（`teacher_id = 当前教师 ID`）。
- 当前设计为一个班级只绑定一个 `teacher_id`，若未来需支持多教师协同管理同一班级，需新增“班级—教师关联表”。
- `status` 字段当前阶段仅预留，列表接口默认只返回 `active` 状态的班级。归档班级功能后置至二期。

## 3. questions

题目主表，当前阶段只支持单选题。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | 自增主键 |
| `question_code` | varchar(64) unique | 题目业务 ID，如 `q_001` |
| `type` | varchar(32) | 当前固定 `single_choice` |
| `knowledge_id` | varchar(64) | 主知识点 ID |
| `stem` | text | 题干 |
| `correct_option` | varchar(8) | 正确选项 |
| `difficulty` | decimal(4,2) | 0-1 难度系数 |
| `explanation` | text null | 解析 |
| `status` | varchar(16) | `active` / `disabled` |
| `created_by` | bigint | 创建教师 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

设计说明：

- 第一阶段只允许一个 `knowledge_id`，不做多知识点映射。若二期迁移至独立 `question_knowledge_mapping` 映射表，需做数据迁移。
- `knowledge_id` 对应 Neo4j 中 `KnowledgePoint.id` 或 Go 侧统一知识点主键。
- 题目全局共享，所有教师共享题库均可查看和使用；修改/删除权限仅限 `created_by` 对应教师。修改/删除 API 当前阶段暂不实现。
- `status` 字段用于软删除/禁用场景，列表查询接口默认只返回 `active` 状态的题目。当前阶段不实现“禁用题目”API，`status` 仅预留。

`question_code` 生成策略：

- 若前端批量导入时提供了 `questionId`，直接作为 `question_code` 存入（需校验唯一性）。
- 若前端未提供，后端自动生成，格式建议：`q_{自增序号零填充}`，如 `q_00001`。

## 4. question_options

题目选项表。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | 主键 |
| `question_id` | bigint | 关联题目 |
| `option_key` | varchar(8) | 如 `A` / `B` / `C` / `D` |
| `option_text` | text | 选项内容 |
| `sort_order` | int | 排序 |
| `created_at` | datetime | 创建时间 |

约束建议：

- `(question_id, option_key)` 唯一。

## 5. student_answers

学生答题记录表。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | 主键 |
| `student_id` | bigint | 学生 ID |
| `question_code` | varchar(64) | 题目业务 ID，关联 `questions.question_code` |
| `knowledge_id` | varchar(64) | 冗余知识点 ID，便于统计 |
| `selected_option` | varchar(8) | 学生选项 |
| `is_correct` | tinyint(1) | 是否正确 |
| `duration_ms` | int null | 作答耗时 |
| `answered_at` | datetime | 作答时间 |
| `created_at` | datetime | 写入时间 |

索引建议：

- `(student_id, answered_at)`
- `(student_id, knowledge_id)`
- `(question_code, answered_at)`

说明：

- 允许同一学生多次回答同一题（练习场景），因此不设 `(student_id, question_code)` 唯一约束。
- `question_code` 直接存业务 ID（如 `q_001`），与 API 层 `questionId` 语义一致，避免额外的关联查询。
- `question_code` 与 `questions.question_code` 逻辑关联，**不建立物理外键**——允许删题后答题记录仍保留，便于历史统计。

## 6. learning_progress

学生知识点掌握度落盘表。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | 主键 |
| `student_id` | bigint | 学生 ID |
| `knowledge_id` | varchar(64) | 知识点 ID |
| `canonical_name` | varchar(255) | 知识点名称冗余 |
| `mastery_score` | decimal(5,2) | 掌握度 0-100 |
| `status` | varchar(16) | `not_started` / `progressing` / `solid` |
| `correct_rate` | decimal(5,4) | 正确率 |
| `answered_count` | int | 累计作答数 |
| `last_answered_at` | datetime null | 最近作答时间 |
| `created_at` | datetime | 首次学习时间 |
| `updated_at` | datetime | 更新时间 |

约束建议：

- `(student_id, knowledge_id)` 唯一。

说明：

- Redis 是实时主读来源，MySQL 中该表用于落盘、教师报表与恢复。
- `mastery_score` 取值范围 **0-100**，与 Redis 中 `uid:{id}:kp` 的值域一致。注意区分：Neo4j 中 `HAS_COMPETENCY` 边的 `score` 属性取值范围是 **0-1**（经矩阵计算后的能力维度归一化分数），两者虽相关但含义不同。

## 7. competency_snapshots

能力画像快照表。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | 主键 |
| `student_id` | bigint | 学生 ID |
| `competency_code` | varchar(64) | 能力编码 |
| `competency_name` | varchar(128) | 能力名称 |
| `score` | decimal(3,2) | 能力维度值，取值 0-1（经矩阵计算后的归一化分数），与 Neo4j `HAS_COMPETENCY.score` 值域一致 |
| `snapshot_time` | datetime | 快照时间 |
| `source` | varchar(32) | `realtime` / `scheduled` |

约束建议：

- `(student_id, competency_code, snapshot_time)` 联合唯一，防止同一时刻产生重复快照。

用途：

- 教师端查看历史能力变化。
- 对 Redis 中当前值做历史留痕。

## 三、Redis 设计

### 1. 学生知识点掌握度

Key：`uid:{studentId}:kp`

类型：Hash

示例：

```text
uid:201:kp
  kp_001 => 52.00
  kp_002 => 61.50
  kp_003 => 34.00
```

### 2. 学生能力画像

Key：`uid:{studentId}:competency`

类型：Hash

示例：

```text
uid:201:competency
  math => 46
  ml => 58
  dl => 66
  kg => 41
```

### 3. 推荐缓存（可选）

Key：`uid:{studentId}:recommend:{targetId}`

类型：String / JSON

说明：

- 用于短时间缓存推荐路径结果。
- 应设置较短 TTL，避免陈旧结果长期存在。

## 四、Neo4j 设计

## 1. 知识图谱域（Python 写入）

当前代码事实补充：

- 当前 Python 流水线 `pipelines/txt2neo4j` 已真实落库的核心标签是 `KnowledgeNode`，并已建立 `node_id` 唯一约束。
- 文档中历史上使用过 `KnowledgePoint` 命名；为避免前后文混淆，建议后续接口、图库与文档逐步统一为 `KnowledgeNode`。若短期内保留 `KnowledgePoint` 表述，必须在接口层明确 `knowledgeId` 对应的就是图谱节点主键，而不是另外一套路由别名。

节点：

- `Course`
- `KnowledgePoint`（建议统一命名为 `KnowledgeNode`）
- `Competency`
- `Scenario`

关系：

- `CONTAINS`
- `PREREQUISITE_OF`
- `RELATED_TO`
- `MAPS_TO`
- `SUBTOPIC_OF`
- `APPLIES_TO`

补充说明：

- 当前代码里课程知识图谱查询还需要返回稳定跳转标识，前端建议优先消费 `routeKnowledgeId`，并兼容 `knowledgeId` / `slug` / `id`。
- 若后续 Go 在线接口承接 `GET /api/catalog/domains`、`GET /api/graph/subgraph`、`GET /api/knowledge/:knowledgeId`，需要在图谱节点 DTO 中显式保留“内部图节点 ID”和“前端路由知识点 ID”两套语义，避免图展示可用但页面跳转失败。

## 2. 前沿知识域（Python 离线写入，Go 在线读取）

该部分用于承接 `frontier-knowledge-pipeline.md` 中定义的“课程知识点 + 前沿论文/行业知识”链路。当前仓库已存在本体配置 `pipelines/txt2neo4j/config/frontier_ontology.json`，但论文抓取、摘要清洗、主题抽取、digest 生成与在线读取接口仍属于待补齐能力。

建议节点：

- `Paper`
- `ResearchTopic`
- `Venue`
- `Author`
- `FrontierDigest`

建议字段：

### `Paper`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `paper_id` | string | 论文唯一 ID |
| `title` | string | 论文标题 |
| `abstract` | text | 摘要 |
| `year` | int | 年份 |
| `venue` | string | 会议 / 期刊名称 |
| `url` | string | 原始链接 |
| `source` | string | 数据来源，如 `arxiv` / `openalex` |
| `updated_at` | datetime | 最近更新时间 |

### `ResearchTopic`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `topic_id` | string | 主题唯一 ID |
| `name` | string | 主题名称 |
| `canonical_name` | string | 规范化主题名 |
| `keywords` | string[] | 关键词集合 |
| `summary` | text | 主题摘要 |

### `Venue`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `venue_id` | string | 会议 / 期刊唯一 ID |
| `name` | string | 名称 |
| `type` | string | `conference` / `journal` |
| `rank` | string | 分区或评级 |

### `Author`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `author_id` | string | 作者唯一 ID |
| `name` | string | 作者姓名 |
| `affiliation` | string | 机构 |

### `FrontierDigest`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `digest_id` | string | 摘要唯一 ID |
| `knowledge_id` | string | 关联课程知识点 ID |
| `knowledge_name` | string | 关联课程知识点名称 |
| `summary` | text | 前沿扩展摘要 |
| `status` | string | `ready` / `stale` / `failed` |
| `generated_at` | datetime | 生成时间 |

建议关系：

- `(:Paper)-[:MENTIONS_TOPIC]->(:ResearchTopic)`
- `(:Paper)-[:PUBLISHED_IN]->(:Venue)`
- `(:Paper)-[:AUTHORED_BY]->(:Author)`
- `(:ResearchTopic)-[:EXTENDS_KNOWLEDGE]->(:KnowledgeNode)`
- `(:FrontierDigest)-[:CURATED_FOR]->(:KnowledgeNode)`
- `(:FrontierDigest)-[:SUMMARIZES_PAPER]->(:Paper)`

设计说明：

- 前沿知识域建议继续由 Python 离线任务写入，Go 侧只提供只读查询与缓存聚合，不直接维护论文知识实体。
- `GET /api/frontier/briefing?knowledgeId={id}` 更适合读取 `FrontierDigest + Topic + Paper` 聚合结果，而不是在在线链路里临时拼装全文。
- 前沿知识允许最终一致，不要求与课程图谱同步强一致。

## 3. 用户能力图谱域（Go 写入）

节点：

- `User`
- `Competency`

关系：

- `HAS_COMPETENCY { score, snapshot_time }`
  - `score` 取值范围 **0-1**（能力维度归一化分数），由 Go Competency 模块对掌握度向量（0-100）执行权重矩阵计算后归一化得出。

说明：

- Go 在线服务负责把用户能力画像异步写回 Neo4j。
- Python 不写用户能力图谱域。

## 五、教师端相关约束

### 1. 前端负责文件解析

教师端导入流程建议：

- 前端解析 Excel / CSV
- 前端做基础列校验
- 前端把结构化 JSON 提交给后端
- 后端只负责业务校验与批量写库

好处：

- 后端不需要引入复杂文件解析依赖
- 错误提示能在前端更细粒度呈现
- API 契约更稳定，上传与解析职责分离

### 2. 学生禁止自主注册

当前阶段：

- 学生账号必须由教师创建或导入
- 不开放学生端 `register`
- 这样更符合班级制、封闭教学管理场景

### 3. 教师与管理员同责

当前阶段不再单独设计管理员表。

做法：

- 所有教师统一 `role = teacher`
- 教师可创建教师、创建班级、导入学生、导入题目
- 真正需要细粒度权限时，再加 `permissions` 或拆 `admin` 角色

## 六、推荐系统数据支撑建议

推荐“下一步学什么知识点”不能只查 Neo4j 邻居点。

建议组合三类数据：

- Neo4j：召回候选知识点
- Redis / MySQL：过滤与打分所需状态数据
- Go Recommend 模块：做规则排序

最小推荐打分可参考：

`score = prerequisite_gap + weakness + goal_match - repeat_penalty - difficulty_penalty`

需要的数据来源：

- `learning_progress`
- `student_answers`
- Redis 中的实时掌握度向量
- Neo4j 中的先修 / 关联关系

## 七、索引建议

### MySQL 索引

- `users(email)` unique
- `users(student_no)` unique
- `users(class_id, role)`
- `classrooms(teacher_id)`
- `questions(question_code)` unique
- `questions(knowledge_id)`
- `student_answers(student_id, answered_at)`
- `student_answers(student_id, knowledge_id)`
- `student_answers(question_code, answered_at)`
- `learning_progress(student_id, knowledge_id)` unique
- `competency_snapshots(student_id, competency_code, snapshot_time)` unique
- 若二期落地前沿知识缓存，建议补充：
  - `frontier_paper_sync_jobs(source, status, started_at)`
  - `frontier_digest_cache(knowledge_id, status)` unique 或半唯一策略
  - `frontier_knowledge_mapping_audit(topic_id, knowledge_id, review_status)`

### Neo4j 索引 / 约束

建议至少建立：

- `KnowledgePoint.id` 唯一约束；若代码实现已统一为 `KnowledgeNode.node_id`，则以 `KnowledgeNode.node_id` 为准
- `Course.id` 唯一约束
- `Competency.id` 唯一约束
- `User.uid` 唯一约束
- 二期前沿知识域建议补充：
  - `Paper.paper_id` 唯一约束
  - `ResearchTopic.topic_id` 唯一约束
  - `Venue.venue_id` 唯一约束
  - `Author.author_id` 唯一约束
  - `FrontierDigest.digest_id` 唯一约束

## 八、当前暂不实现的数据能力

当前阶段后置：

- 通用行为埋点明细表
- 文件原始上传记录表
- 多知识点题目映射表
- 班级作业 / 任务分发表
- 推荐采纳反馈表
- 前沿论文抓取批次表、digest 缓存表、topic 映射审计表的正式建表与调度闭环
- `GET /api/catalog/domains`、`GET /api/recommend/projects` 等面向前端静态兜底数据替换的在线目录 / 推荐接口

这些能力可以在第二阶段再补。

但为了减少前后端联调歧义，建议文档层先明确：

- 当前首页知识目录仍可能由前端静态数据兜底，不代表后端目录接口已具备。
- 当前前沿知识域属于“数据模型已定义、在线能力未补齐”的阶段，不应把 `GET /api/frontier/briefing` 视为已经落地的现有接口。
