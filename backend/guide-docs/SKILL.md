# Go 单体后端架构指导

## 适用场景

当用户要开发一个新的 Go 单体后端项目，且具备以下特征时，优先使用本 Skill：
- 使用 `Gin` 作为 HTTP 框架。
- 使用 `GORM` 访问 MySQL。
- 同时使用 `MySQL / Neo4j / Redis`。
- 采用标准三层：`router/handler -> service -> repository`。
- 数据量较低，系统复杂度中等，更强调可维护性、稳定性与开发效率，而不是超大规模分布式能力。

## 核心原则

1. **先保留清晰边界，再考虑抽象复用。**
2. **单体项目优先简单直接，不预埋微服务级复杂度。**
3. **基础设施统一收口，业务模块保持薄而清晰。**
4. **错误、日志、配置、响应格式必须统一。**
5. **Redis 只做加速与协作，不做唯一真相。**
6. **依赖注入优先手动构造，不急于引入 DI 框架。**
7. **测试重点放在 service 正确性与 repository 集成正确性。**

## 产出要求

在使用本 Skill 回答时，应从“架构师 + 资深后端工程师”视角输出，至少覆盖：
- 推荐目录结构。
- 各层职责边界。
- Gin 中间件体系。
- 配置组织方式。
- 依赖注入方案。
- DTO、entity、response 的边界。
- GORM 使用规范。
- Redis 键、TTL、常量、魔法字符串治理。
- Neo4j 使用边界。
- 优雅停机与资源生命周期管理。
- 错误码、统一响应、日志与链路追踪。
- 错误处理规范、分层错误边界与返回策略。
- 日志书写规范与日志字段约束。
- 注释规范与注释边界。
- 代码组织规范、模块拆分与文件边界。
- 测试策略与测试金字塔。
- 可观测性、安全性、上线与迁移建议。
- 明确指出哪些是**应该继承**的经验，哪些是**不该照搬**的微服务遗产。

## 默认推荐结论

### 1. 推荐分层
首选四层，而不是过度细分：
- `handler`：参数绑定、鉴权上下文提取、统一响应。
- `service`：业务规则、事务编排、领域校验。
- `repository`：MySQL / Neo4j / Redis 访问。
- `pkg`：仅放跨模块横切能力。

### 2. 不建议一开始引入的复杂度
以下能力默认不建议预埋：
- 微服务网关代理层。
- protobuf 转换链。
- 熔断器、补偿队列、复杂异步同步器。
- 全量接口化。
- 读写分离、复杂分库分表预埋。

### 3. 强烈建议保留的共性能力
- 统一业务错误模型。
- 统一 HTTP 响应结构。
- 统一日志字段。
- 请求级 `trace_id`。
- Redis key builder 与 TTL 常量。
- 手动依赖注入。
- 优雅停机。
- repository 层错误翻译。

## 回答风格要求

输出应：
- 使用中文。
- 先给总体结论，再展开各项设计。
- 对需要取舍的地方给出“推荐方案 / 不推荐方案 / 原因”。
- 明确区分“适合低数据量单体”的简化方案与“未来可演进”的保留点。
- 如果用户要落地脚手架，可继续输出目录树、模块模板、配置结构与初始化顺序。
