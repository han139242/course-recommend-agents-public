# Go 单体后端详细开发指导

## 一、总体设计思想

对于用户规模约 200 人、使用 `Gin + GORM + MySQL + Neo4j + Redis` 的单体后端，架构目标不应是“为未来无限扩展预埋复杂分布式能力”，而应是：

1. **边界清晰**：每一层职责稳定。
2. **稳定优先**：错误处理、日志、停机流程、配置可控。
3. **易维护**：半年后还能快速定位问题。
4. **易测试**：关键逻辑能低成本验证。
5. **可演进**：未来若拆模块或拆服务，不需要推倒重来。

一句话建议：

**做一个工程化扎实的单体，而不是一个假装自己是微服务的单体。**

### 设计说明

#### `cmd/server`
只保留程序入口，不写业务逻辑。

#### `internal/bootstrap`
放应用装配逻辑。`main.go` 只做三件事：
- 读取配置。
- 创建应用。
- 启动并等待退出信号。

#### `internal/config`
定义强类型配置结构，不把环境变量读取散落到业务层。

#### `internal/module/<name>`
以业务模块为单位组织，而不是按技术类型平铺整个仓库。这会比全局 `handler/service/repository` 大目录更容易维护。

#### `internal/repository/mysql|neo4j|redis`
如果多个业务模块共享一类底层封装，可在这里沉淀通用仓储基类或辅助查询能力。但不要把所有业务查询都挤在这里。

#### `pkg`
只放横切能力，不放强业务语义代码。适合放：
- 错误模型。
- 日志封装。
- 上下文元数据。
- 响应结构。
- 常量与 key builder。

## 三、分层职责边界

### 1. handler 层
职责：
- 绑定 path/query/body/header。
- 调用参数校验。
- 从上下文获取用户身份、设备、trace 信息。
- 调用 service。
- 将结果转成统一响应。

不应该做：
- 复杂业务判断。
- 事务控制。
- SQL / Cypher / Redis 操作。
- 拼接复杂错误码。

### 2. service 层
职责：
- 承载业务规则。
- 编排多个 repository。
- 管理事务边界。
- 做领域状态判断。
- 控制缓存一致性策略。

不应该做：
- 直接依赖 gin。
- 返回 HTTP 语义对象。
- 写原始 SQL / Cypher。

### 3. repository 层
职责：
- 封装 MySQL / Neo4j / Redis 的数据访问。
- 屏蔽底层驱动错误差异。
- 提供面向业务的持久化接口。

不应该做：
- 编排复杂业务流程。
- 夹带 HTTP 上下文语义。
- 输出不稳定的驱动层错误给 service。

### 4. DTO / Entity / Response
建议严格区分：
- `dto/request`：HTTP 输入。
- `dto/response`：HTTP 输出。
- `entity/model`：数据库或领域对象。
- `command/query`：service 层输入对象，可按需引入。

不要让以下三者混为一体：
- Gin 绑定对象。
- GORM Model。
- 对前端输出 JSON。

## 四、Gin 中间件设计

单体项目推荐的中间件链：

1. `RequestID`
2. `RealIP`
3. `Logger`
4. `Recovery`
5. `CORS`（如需要）
6. `Auth`
7. `RateLimit`（按接口或按用户）

### 1. 日志中间件
日志中间件应该输出**单条聚合访问日志**，不要在一次请求里打印过多碎片日志。

建议字段：
- `trace_id`
- `method`
- `path`
- `query`
- `status`
- `cost`
- `client_ip`
- `user_id`
- `business_code`

建议策略：
- 2xx/3xx：`Info`
- 4xx：通常 `Warn` 或 `Info`，看业务需求
- 5xx：`Error`
- 慢请求：单独提升为 `Warn`
- 健康检查：降噪或跳过

### 2. 恢复中间件
Recovery 中间件要做的不是简单 `recover()`，而是：
- 捕获 panic。
- 识别 `broken pipe / connection reset by peer`。
- 记录必要请求元信息。
- 输出脱敏后的错误响应。
- 记录结构化堆栈。

注意：
- 不要默认把完整 body 或敏感 header 落日志。
- 如果要记录 request dump，必须做脱敏白名单控制。

### 3. 链路追踪
对这个体量的单体项目，不一定一开始就接 OpenTelemetry，但必须有轻量版链路语义：
- 每个请求生成 `trace_id`。
- `trace_id` 写入日志。
- 响应头回写 `X-Request-ID` 或标准 trace 头。
- 异步任务、数据库日志、Redis 操作日志尽量带上 trace 语义。

推荐先做轻量实现，未来再平滑升级到正式 tracing。

### 4. 认证中间件
认证中间件只做：
- 提取 token。
- 校验 token。
- 注入 `user_id / device_id / role` 到 context。

不要做：
- 复杂业务权限判断。
- 查询一堆业务数据。

权限判断更适合：
- 简单场景：handler 层。
- 复杂场景：service 层。

## 五、依赖注入与解耦

### 推荐方案：手动依赖注入
对这个规模的单体项目，最合适的是：
- 构造函数注入。
- 在 `bootstrap` 层统一装配。
- 明确依赖链。

示例装配顺序：
- config
- logger
- mysql
- neo4j
- redis
- repository
- service
- handler
- router
- http server

### 接口如何使用
不要全量接口化。

推荐原则：
- **跨层依赖且需要 mock 的边界**：定义接口。
- **只有一个实现且不需要替换**：先直接用具体类型。
- **repository 通常值得接口化**。
- **service 是否接口化，取决于测试和模块边界需要**。

错误做法：
- 每个 struct 都先配一个 interface。
- 为了形式统一而制造抽象层。

## 六、资源管理：Redis 键、魔法数字、魔法字符串

### 1. Redis 键管理
必须统一 key builder，禁止业务代码手写 key。

推荐：
- `pkg/key/auth.go`
- `pkg/key/user.go`
- `pkg/key/relation.go`

命名规范建议：
- `auth:token:{userID}:{deviceID}`
- `auth:verify_code:{scene}:{target}`
- `user:profile:{userID}`
- `relation:friend:{userID}`
- `idempotent:{scene}:{id}`

原则：
- 前缀分域。
- 含义稳定。
- 不混大小写。
- 不夹带模糊缩写。

### 2. TTL 管理
TTL 也必须集中管理，例如：
- `const VerifyCodeTTL = 5 * time.Minute`
- `const AccessTokenTTL = 7 * 24 * time.Hour`
- `const EmptyCacheTTL = 1 * time.Minute`

不要在业务里到处散落：
- `5*time.Minute`
- `30*time.Second`
- `86400`

### 3. 魔法数字与字符串
以下内容必须常量化或类型化：
- 状态值。
- 场景类型。
- 事件类型。
- 限流阈值。
- 默认分页大小。
- 排序方向。

更进一步，建议使用 typed const：
- `type VerifyScene string`
- `type UserStatus int`
- `type RelationType string`

## 七、配置设计

### 推荐配置结构
配置分两层：

1. **强类型配置结构**。
2. **从环境变量或配置文件加载**。

例如：
- `AppConfig`
- `HTTPConfig`
- `MySQLConfig`
- `RedisConfig`
- `Neo4jConfig`
- `AuthConfig`
- `LogConfig`

### 配置原则

#### 1. 配置集中读取
业务层不直接 `os.Getenv()`。

#### 2. 默认值明确
开发环境可有合理默认值，但生产关键项必须校验。

#### 3. 启动时校验
必须在启动阶段校验：
- DSN 是否为空。
- 端口是否合法。
- JWT 密钥是否存在。
- Redis 地址是否可用。
- Neo4j 配置是否完整。

#### 4. 打印生效配置摘要
启动日志建议打印非敏感配置摘要，便于排查部署问题。

#### 5. 不过度依赖大而全配置框架
对小型单体，简单的 `env + struct + validate` 就足够了。

## 八、DTO 设计

### 建议
每个模块单独维护 DTO：
- `create_user_request.go`
- `update_user_request.go`
- `user_response.go`

如果模块不大，也可以按聚合放一起，但不要把所有模块 DTO 堆在一个目录下。

### 要点
- 请求 DTO 只面向接口输入。
- 响应 DTO 只面向接口输出。
- 不要把数据库字段标签直接暴露到 API 结构。
- 对外输出字段应主动设计，而不是把 entity 原样 JSON 化。

### 参数校验
建议统一采用：
- Gin 绑定 + validator 标签。
- 复杂跨字段校验放 service。

例子：
- 格式校验在 DTO。
- “开始时间不能大于结束时间”可放 DTO 自定义校验或 service。
- “该用户不能重复创建关系”必须放 service。

## 九、GORM 使用规范

### 1. Model 与 Entity
对小型单体，可以适度统一，但建议至少区分：
- 持久化模型。
- 对外响应对象。

### 2. Repository 中统一 `WithContext`
所有数据库操作都要：
- `db.WithContext(ctx)`

这样便于：
- 日志带 trace。
- 未来接入 tracing。
- 超时与取消控制。

### 3. 错误翻译
repository 层应翻译底层错误，例如：
- `gorm.ErrRecordNotFound -> ErrNotFound`
- 唯一键冲突 -> `ErrConflict`
- 外键约束失败 -> `ErrConstraint`

service 层不要直接判断驱动错误文本。

### 4. 事务边界
事务应由 service 控制，而不是 handler 或 repository 控制。

适合放事务的场景：
- 多表写入。
- 状态变更 + 事件记录。
- MySQL 与缓存更新需要明确顺序控制。

建议：
- 提供 `RunInTx(ctx, func(txRepo ... ) error)` 或统一事务管理器。
- 事务中避免做外部网络调用。

### 5. 查询策略
- 明确 select 字段，避免无脑 `SELECT *`。
- 分页必须设置上限。
- 列表接口默认排序必须稳定。
- 预加载只在必要时使用。
- 对低数据量项目，性能不是第一矛盾，但坏查询习惯会制造维护问题。

### 6. Migration
建议显式管理迁移，不依赖启动时自动迁移生产库。

推荐：
- 开发环境可辅助自动迁移。
- 生产环境使用明确 migration 脚本。

## 十、Neo4j 使用建议

既然项目用了 Neo4j，就必须明确它的职责边界。

### 推荐使用场景
适合放到 Neo4j 的通常是：
- 社交关系。
- 推荐关系。
- 图遍历。
- 多跳关系查询。

### 不推荐使用场景
以下内容依旧建议 MySQL 为主：
- 用户基础资料。
- 登录认证主数据。
- 订单、账单、配置类核心事务数据。

### 建议原则
- **MySQL 是主真相源，Neo4j 是关系型补充**。
- 如果一份数据同时存在 MySQL 与 Neo4j，必须明确谁是源头。
- 跨库一致性优先做“可恢复的一致性”，不要一开始追求分布式强一致。

### repository 设计建议
可按存储类型拆仓储实现：
- `UserMySQLRepository`
- `RelationGraphRepository`
- `RelationCacheRepository`

service 统一编排，不要让 handler 感知底层使用了图数据库。

## 十一、统一错误模型与统一响应

### 1. 统一错误模型
建议定义应用级错误：
- `code`
- `message`
- `cause`
- `logged`

原则：
- 内部保留丰富信息。
- 对外暴露稳定且脱敏的错误语义。
- 避免同一个错误多次重复打日志。

### 2. 统一响应结构
推荐统一返回：
- `code`
- `message`
- `data`
- `trace_id`
- `timestamp`

### 3. HTTP 状态码建议
对单体项目，我更推荐：
- 400：参数错误。
- 401：未认证。
- 403：无权限。
- 404：资源不存在。
- 409：冲突。
- 429：限流。
- 500：系统异常。

同时 body 中保留业务码。

不建议无脑“所有业务错误都返回 200”，除非前端体系强依赖此约定。

## 十二、错误处理规范

错误处理在单体项目里是稳定性的核心，不是“能返回就行”。

目标应该是：
- 对内错误信息充分。
- 对外错误语义稳定。
- 分层边界明确。
- 业务错误和系统错误严格区分。
- 日志记录点统一，不重复刷屏。

### 1. 错误分层原则

#### handler 层
负责：
- 参数绑定错误转换成统一参数错误。
- service 返回错误转换成 HTTP 状态码 + 统一响应体。
- 不向前端暴露底层错误细节。

不负责：
- 拼接数据库或驱动错误文案。
- 处理底层技术细节。

#### service 层
负责：
- 把 repository 错误翻译为业务语义错误。
- 决定某个异常是业务失败还是系统失败。
- 为统一错误对象附加业务码。
- 控制是否继续向上抛出。

不负责：
- 直接输出 HTTP 语义。
- 直接返回 gin 响应。

#### repository 层
负责：
- 把 GORM / Redis / Neo4j 驱动错误翻译成稳定的仓储层错误语义。
- 保留原始 cause，便于日志和排障。

不负责：
- 直接定义前端业务提示语。
- 把驱动错误原样泄漏到 handler。

### 2. 推荐错误分类
建议至少区分以下几类：

#### 业务错误
例如：
- 用户不存在。
- 密码错误。
- 验证码错误。
- 状态不允许。
- 权限不足。
- 资源冲突。

特点：
- 可预期。
- 可稳定映射为业务码。
- 不一定需要打 Error 日志。

#### 系统错误
例如：
- MySQL 不可用。
- Redis 超时。
- Neo4j 查询失败。
- JSON 序列化异常。
- panic。

特点：
- 不可预期或不应频繁发生。
- 通常应打 Error 日志。
- 对外应脱敏处理。

#### 边界错误
例如：
- 参数绑定失败。
- 参数校验失败。
- 上下文缺少必要身份信息。
- 非法请求头。

特点：
- 通常映射为 400/401/403。
- 不属于系统故障。

### 3. 仓储层错误翻译建议
repository 层不要把底层错误直接丢给 service 做文本判断。

建议至少统一以下语义：
- `ErrNotFound`
- `ErrConflict`
- `ErrConstraint`
- `ErrCacheMiss`
- `ErrDependencyUnavailable`

例如：
- `gorm.ErrRecordNotFound -> ErrNotFound`
- 唯一键冲突 -> `ErrConflict`
- `redis.Nil -> ErrCacheMiss`
- 驱动超时 -> `ErrDependencyUnavailable`

这样 service 只关心业务语义，不关心底层库差异。

### 4. 业务错误码设计建议
业务错误码建议满足：
- 稳定。
- 可枚举。
- 可分模块。
- 可长期兼容。

推荐思路：
- 参数错误一段。
- 认证授权一段。
- 用户模块一段。
- 关系模块一段。
- 系统错误一段。

不要：
- 到处散落裸数字。
- 用错误 message 代替错误码。
- 同一个错误在不同模块返回不同 code。

### 5. 错误返回策略

#### 参数错误
返回：
- HTTP 400
- 稳定业务码
- 可读 message

#### 未认证 / 无权限
返回：
- HTTP 401 / 403
- 不暴露内部认证细节

#### 资源不存在
返回：
- HTTP 404
- 资源语义清晰

#### 冲突类错误
返回：
- HTTP 409
- 比如重复创建、重复提交、状态冲突

#### 系统异常
返回：
- HTTP 500
- 通用脱敏 message
- 不返回原始驱动错误文本

### 6. 对外错误信息脱敏原则
对客户端返回的 `message` 应该：
- 能理解。
- 稳定。
- 不泄漏实现细节。

不要返回：
- SQL 语句。
- Redis 驱动错误原文。
- Neo4j 查询原文。
- 文件路径。
- 堆栈。
- 内部服务地址。

推荐：
- `系统繁忙，请稍后再试`
- `资源不存在`
- `参数错误`
- `当前状态不允许该操作`

### 7. 错误包装建议
推荐保留两层信息：
- 面向业务的稳定错误语义。
- 面向排障的原始 cause。

例如应用错误对象中可以包含：
- `code`
- `message`
- `cause`
- `op`
- `logged`

其中：
- `message` 给上层统一响应使用。
- `cause` 只给日志和排障使用。
- `op` 可选，用于标识出错操作，例如 `user_service.create_user`。

### 8. 哪一层该打日志
推荐规则：
- repository：只有在补充底层上下文非常必要时才记录，避免无脑打 Error。
- service：做业务翻译时通常不重复记录同级错误。
- handler / middleware / recovery：作为最终出口决定是否记录错误。
- panic：统一由 recovery 打一次完整错误日志。

记住一个原则：

**错误可以逐层包装，但不应该逐层都打同等级错误日志。**

### 9. `panic` 的处理边界
`panic` 只适合表示真正的程序异常，不应当作普通业务分支使用。

必须通过 recovery 统一处理：
- 捕获 panic。
- 记录结构化堆栈。
- 输出统一 500。
- 不把 panic 内容原样返回给客户端。

不允许：
- 用 `panic` 代替业务错误返回。
- 在业务代码中用 `panic` 表达“查不到数据”或“参数不对”。

### 10. 校验错误处理建议
参数校验建议分两层：

#### DTO 层校验
处理：
- 必填。
- 长度。
- 格式。
- 枚举值。

#### service 层校验
处理：
- 业务状态是否合法。
- 资源之间关系是否合法。
- 是否重复提交。
- 是否允许当前用户操作。

这样可以避免把业务规则硬塞进 DTO 标签。

### 11. 缓存与错误处理
Redis 不是主真相源，因此缓存错误处理要分级：

#### 缓存读取失败
- 优先降级回源 MySQL。
- 记录必要日志。
- 不要轻易把整个主流程打挂。

#### 缓存写入失败
- 视业务重要性决定：忽略、重试、异步补偿。
- 对低数据量单体，多数情况下一次短重试 + 记录日志就够了。

#### 空值缓存
- 要与正常缓存区分 TTL。
- 要防止把系统错误误写成空值缓存。

### 12. 事务与错误处理
事务内出错要明确：
- 是否回滚。
- 是否包装成业务错误。
- 是否记录错误日志。

推荐原则：
- 只要事务函数返回 error，就统一回滚。
- 事务中不要发外部网络请求。
- 如果事务失败属于底层依赖问题，应统一转换为系统错误。

### 13. 推荐反模式
以下是典型错误处理反模式：
- 用字符串比较判断错误类型。
- 直接把 `err.Error()` 返回给前端。
- 同一个错误层层打 Error。
- repository 直接返回 HTTP 语义。
- service 直接操作 gin context。
- 用 `panic` 处理业务失败。
- 所有业务失败都打 Error 导致日志污染。
- 使用裸数字表示错误码。

### 14. 最终结论
一个好的单体后端错误处理体系应该做到：
- 仓储层翻译底层错误。
- 服务层翻译业务语义。
- 接口层翻译协议语义。
- Recovery 兜底未知异常。
- 日志只在关键处理点记录一次。
- 对外永远稳定、脱敏、可预期。

## 十三、优雅停机

优雅停机不是“收到信号就退出”，而是一个资源释放顺序问题。

### 推荐顺序
1. 停止接收新请求。
2. 等待在途请求完成。
3. 停止后台 worker / 定时任务。
4. 刷新或结束必要缓冲。
5. 关闭 MySQL / Neo4j / Redis 等外部连接。
6. 退出进程。

### 关键点
- `http.Server.Shutdown(ctx)` 必须设置超时。
- 后台 goroutine 应该受统一 context 管理。
- worker 停止必须可等待，不要直接丢失任务状态。
- 停机日志要明确打印阶段。

### 推荐做法
在 `bootstrap/shutdown.go` 中统一注册关闭函数，例如：
- HTTP Server
- Cron
- Async Worker
- Redis Client
- Neo4j Driver
- SQL DB

然后按顺序执行。

## 十三、日志设计

### 推荐规范
- 使用结构化日志。
- 默认 JSON 输出。
- 自动注入上下文字段：`trace_id / user_id / device_id`。
- 单次请求只打一条访问日志。
- 系统错误输出堆栈。

### 日志层级建议
- `Debug`：开发诊断。
- `Info`：正常业务行为。
- `Warn`：慢请求、可恢复异常、可疑行为。
- `Error`：系统失败、panic、依赖故障。

### 日志书写规范

#### 1. 日志消息要写“发生了什么”，不要写成变量转储
推荐：
- `用户登录失败`
- `查询好友列表失败`
- `Redis 写入验证码缓存失败`
- `MySQL 事务提交失败`

不推荐：
- `login error`
- `err`
- `这里出错了`
- `执行到这里了`

日志消息应该表达事件语义，具体细节放在结构化字段里。

#### 2. 统一使用结构化字段，不拼接大串文本
推荐：
- `logger.Error(ctx, "查询用户失败", logger.String("user_id", userID), logger.ErrorField("error", err))`

不推荐：
- `logger.Error(ctx, "查询用户失败: "+userID+": "+err.Error())`

原则：
- 消息负责概括事件。
- 字段负责承载检索信息。
- 避免把可检索信息塞进 message 文本。

#### 3. 字段命名要稳定
建议长期固定以下字段名：
- `trace_id`
- `user_id`
- `device_id`
- `request_id`
- `method`
- `path`
- `status`
- `cost`
- `business_code`
- `error`

不要同一个含义混用：
- `uid / userId / user_id`
- `duration / latency / cost_ms`

一旦字段命名稳定，后续日志检索、告警、看板才不会混乱。

#### 4. 同一错误只在最终处理点重点记录一次
建议：
- repository 返回错误，不急着打 Error，除非要补充底层上下文。
- service 做业务翻译时，通常不重复打同级错误。
- handler / middleware / 统一异常出口再决定是否记录最终错误日志。

否则会出现同一失败在 3 到 5 层重复刷屏。

#### 5. 业务预期失败与系统失败分开
这些通常属于业务预期失败：
- 用户名或密码错误。
- 验证码错误。
- 资源不存在。
- 权限不足。

它们通常不应该打成 `Error`，多数场景下：
- 打 `Info` 或 `Warn`
- 或完全不单独记录，只保留访问日志里的业务码

这些才更适合打 `Error`：
- 数据库不可用。
- Redis 超时。
- Neo4j 查询异常。
- panic。
- 外部依赖失败导致主流程不可用。

#### 6. 敏感信息绝不入日志
禁止直接记录：
- 密码。
- token / refresh token。
- 验证码明文。
- 身份证号、手机号全量、邮箱全量（如业务敏感）。
- 数据库连接串中的密码。
- 请求 body 中的敏感字段。

如果确实需要排查，应采用：
- 掩码。
- 白名单字段。
- 测试环境限定输出。

#### 7. 访问日志、业务日志、审计日志分层
建议区分三类：
- 访问日志：每个请求一条，用于流量与排障。
- 业务日志：关键业务动作，用于定位流程问题。
- 审计日志：敏感操作留痕，用于安全与追责。

不要把三种日志混成一种。

#### 8. 日志量要可控
低数据量项目也要避免日志噪声：
- 健康检查接口默认降噪。
- 高频轮询接口尽量只保留访问日志。
- 循环中的 Debug 日志谨慎开启。
- 批处理场景优先打印汇总，不逐条刷日志。

### 不建议
- 大量 `fmt.Println`。
- 日志内容依赖字符串拼接。
- 在每一层都重复记录同一个错误。
- 把请求完整 body 和敏感 header 无差别打到日志。

原则：
- **错误在哪被最终处理，通常就在哪打最终错误日志。**
- **日志首先服务排障，其次服务审计，最后才是“看起来有输出”。**

## 十四、注释规范

### 注释的总原则
注释应该解释：
- 为什么这样设计。
- 这个约束的背景是什么。
- 这段逻辑的边界条件或坑点是什么。
- 为什么不能改成更“直觉”的写法。

不要解释：
- 代码表面已经清楚表达的事情。
- 每一行在“做什么”。
- 为了凑注释而写的废话。

一句话原则：

**注释解释 WHY、约束、取舍和风险，不解释显而易见的 WHAT。**

### 推荐写注释的地方

#### 1. 导出的类型、函数、方法
Go 项目建议对导出符号写文档注释，尤其是：
- 公共构造函数。
- 公共 service 接口。
- 可复用的 pkg 能力。
- 中间件、配置结构、事务辅助器。

#### 2. 非直观的业务规则
例如：
- 为什么某个状态不能逆转。
- 为什么缓存 miss 要写空值缓存。
- 为什么这里先写 MySQL 再删 Redis。
- 为什么 Neo4j 只做关系补充，不作为主真相。

#### 3. 容易踩坑的边界
例如：
- 这里必须带事务。
- 这里不能并发调用。
- 这里不能在事务内请求外部服务。
- 这里依赖唯一索引保障幂等。

#### 4. 临时兼容逻辑
如果历史包袱无法立刻删除，可以写清楚：
- 兼容什么旧行为。
- 计划何时移除。
- 不移除会有什么影响。

### 不推荐写注释的地方

#### 1. 明显的赋值、判断、返回
不推荐：
- `// 设置用户 ID`
- `// 判断是否为空`
- `// 返回结果`

#### 2. 能靠更好命名解决的问题
如果需要靠注释解释变量名，大概率应该先改名。

#### 3. 会快速过期的流水账式注释
不推荐：
- `// 2026-04-04 我在这里修了个 bug`
- `// 这里先这么写，后面再说`

如果真需要记录背景，应写到 issue、PR、文档，或写成明确约束说明。

### 注释风格规范

#### 1. 注释使用中文，术语保留英文
例如：
- `Idempotent（幂等）`
- `trace_id`
- `fallback`

#### 2. 注释与日志一样，要准确、克制
注释要短、准、稳，不要长篇重复代码逻辑。

#### 3. 注释必须跟代码一起维护
如果重构导致注释失真，宁可删掉，也不要保留错误注释。

#### 4. 优先块注释解释约束，不要每行都注释
推荐在函数前或关键分支前解释背景，而不是把代码逐行翻译成中文。

### 推荐示例

推荐：
- `// 这里先查 MySQL，再回填 Redis，避免缓存中脏数据覆盖主库最新结果。`
- `// Neo4j 只维护关系边，不保存用户主资料，主真相仍然在 MySQL。`
- `// 该接口允许重复调用，幂等依赖唯一索引和 Redis 幂等键双重保障。`

不推荐：
- `// 查询 MySQL`
- `// 设置 Redis`
- `// 调用 service`

### 文档注释建议
对于导出结构，建议保持统一句式：
- 这个类型/函数做什么。
- 它的边界或关键约束是什么。

例如：
- `// UserService 负责用户领域的核心业务编排，不直接暴露底层存储细节。`
- `// RunInTx 在单个数据库事务中执行业务函数，禁止在事务内发起外部网络调用。`

## 十五、代码组织规范

代码组织规范的目标，不是把目录堆得很复杂，而是让人看到文件位置就大致知道：
- 这段代码解决什么问题。
- 它属于哪一层。
- 它依赖谁。
- 它能不能被别的模块直接使用。

低数据量单体项目尤其要避免两种极端：
- 所有代码都堆在几个大文件里。
- 为了“架构感”提前拆出大量空壳目录和抽象层。

推荐原则是：

**按业务模块组织，按分层职责拆文件，按复用价值决定是否抽公共包。**

### 1. 目录组织原则

#### 优先按业务模块聚合
推荐：
- `internal/module/user/...`
- `internal/module/relation/...`
- `internal/module/auth/...`

不推荐整个仓库只有：
- `internal/handler`
- `internal/service`
- `internal/repository`

后者在模块少时看起来简单，但随着功能增长，跨模块文件会迅速混在一起。

#### 模块内再分层
每个模块内再按职责拆：
- `handler`
- `service`
- `repository`
- `dto`
- `entity`
- `types`（按需）

这样既保留业务聚合，又保留清晰分层。

### 2. 一个模块应该包含什么
一个中等规模业务模块，推荐至少包含：
- `handler`：接口入口。
- `service`：业务编排。
- `repository`：数据访问。
- `dto`：请求/响应对象。
- `entity`：领域对象或持久化对象。

可选包含：
- `types`：枚举、状态、值对象。
- `assembler` / `converter`：复杂转换逻辑。
- `policy`：复杂策略判断。
- `validator`：复杂业务校验。

如果模块很小，不要为了形式把这些目录全建齐。可以先保留最小集合。

### 3. 每层允许放什么

#### handler 文件里允许放
- 路由入参绑定。
- header / path / query / body 提取。
- 调用 service。
- 调用统一响应封装。
- 少量协议层适配辅助函数。

#### handler 文件里不允许放
- SQL / Cypher / Redis 操作。
- 核心业务分支。
- 事务控制。
- 大量 DTO 与 entity 转换。

#### service 文件里允许放
- 业务主流程。
- 事务边界。
- 多 repository 编排。
- 业务校验与状态流转。
- 缓存一致性策略。

#### service 文件里不允许放
- 直接依赖 gin。
- 直接拼 HTTP 响应。
- 大量协议字段绑定逻辑。

#### repository 文件里允许放
- GORM 查询。
- Neo4j 查询。
- Redis 读写。
- 底层错误翻译。
- 按存储特性封装数据访问。

#### repository 文件里不允许放
- 业务语义编排。
- handler 上下文处理。
- 前端返回文案。

### 4. 文件拆分原则

#### 按业务动作拆，而不是按 CRUD 机械拆
例如用户模块可以拆成：
- `create_user.go`
- `update_user_profile.go`
- `reset_password.go`
- `list_users.go`

而不是一股脑放进：
- `user_service.go`

对复杂模块，这种“按业务动作拆文件”的可读性会更高。

#### 当一个文件满足以下任一条件时，应该考虑拆分
- 超过 300~500 行。
- 同时承担多个独立业务动作。
- 同时处理写流程和读流程。
- 出现多个完全不同的依赖组合。
- 测试文件开始变得难以定位。

#### 不要为了追求短文件而过度拆分
如果一个文件只有十几行，且强依赖上下文才能理解，不如合并。

拆分的目标是提高理解成本表现，不是追求“文件越小越高级”。

### 5. DTO、Entity、Model 的组织方式

#### DTO
推荐按接口语义拆分：
- `create_user_request.go`
- `create_user_response.go`
- `list_user_response.go`

如果模块较小，也可以：
- `user_request.go`
- `user_response.go`

#### Entity / Model
如果你的领域对象和数据库模型高度一致，可以适度合并。

但以下情况建议分开：
- 数据库存储字段很多，但业务只关注一部分。
- 存在派生字段。
- MySQL 与 Neo4j 中对象结构不同。
- 输出给前端的结构与存储结构差异大。

### 6. 跨模块依赖规范

#### 允许的依赖方向
推荐依赖方向：
- `handler -> service -> repository`
- `service -> pkg`
- `repository -> pkg`

#### 不推荐的依赖方向
- `repository -> handler`
- `repository -> service`
- `service A -> handler B`
- 模块 A 直接操作模块 B 的 repository 实现

#### 跨模块调用建议
如果模块 A 需要模块 B 的能力：
- 优先依赖 B 的 service 能力边界。
- 不要直接摸到 B 的 repository 细节。

否则后续模块边界会越来越脆。

### 7. 何时抽公共包 `pkg`
只有同时满足以下条件时，才值得抽到 `pkg`：
- 被多个模块复用。
- 不带强业务语义。
- 抽出来后比留在模块内更清晰。

适合抽到 `pkg` 的：
- `apperr`
- `logger`
- `result`
- `ctxmeta`
- `key`
- 通用分页结构
- 通用事务辅助器

不适合抽到 `pkg` 的：
- 用户领域规则。
- 关系推荐策略。
- 具体业务状态机。
- 面向单一模块的 helper。

判断标准：

**如果离开当前业务上下文，这段代码还能成立，才考虑进 `pkg`。**

### 8. helper / util 的使用规范
尽量避免在项目里泛滥以下目录：
- `utils`
- `helpers`
- `common`

这些目录经常会演变成“什么都能塞”的垃圾桶。

更推荐：
- 语义明确地放进模块内。
- 或放进有明确职责的 `pkg/apperr`、`pkg/key`、`pkg/result`。

如果你发现一个函数只能被一个模块理解，那它通常不该放 `utils`。

### 9. router 组织方式
推荐：
- 顶层 `router/router.go` 负责创建引擎与挂全局中间件。
- `router/v1.go` 负责版本路由注册。
- 每个模块导出自己的注册函数，例如：
  - `RegisterUserRoutes`
  - `RegisterAuthRoutes`

不要把全站所有路由都堆在一个大文件里。

### 10. bootstrap 组织方式
`main.go` 不要承担完整装配细节。

推荐拆成：
- `bootstrap/config.go`
- `bootstrap/logger.go`
- `bootstrap/mysql.go`
- `bootstrap/redis.go`
- `bootstrap/neo4j.go`
- `bootstrap/router.go`
- `bootstrap/shutdown.go`

这样有几个好处：
- 启动逻辑清楚。
- 每种依赖初始化可以单测或单独调整。
- main 文件不会膨胀。

### 11. 测试文件的组织方式
建议测试跟着业务文件走：
- `service/create_user_test.go`
- `repository/user_repository_integration_test.go`
- `handler/create_user_handler_test.go`

不要把整个仓库的大量单元测试全堆到一个 `test` 目录下。

但以下测试适合独立目录：
- 跨模块集成测试。
- e2e 测试。
- 公共 fixture。

### 12. 何时继续拆子目录
当某个模块继续长大时，可以往下再拆一层，但必须有明确理由。

例如 `user/service` 下继续拆：
- `command/`
- `query/`

适用场景：
- 写流程和读流程差异极大。
- 团队多人同时维护同一模块。
- 模块已经明显超过单目录可维护范围。

如果只是为了“显得专业”，不建议提前拆。

### 13. 推荐反模式
以下是代码组织上的典型反模式：
- 一个模块只有一个几百行 `service.go`。
- 所有模块共用一个 `utils` 目录。
- 所有路由堆在一个文件。
- 所有 DTO 堆在一个文件。
- 模块 A 直接访问模块 B 的 repository 实现。
- `pkg` 里塞满业务代码。
- 为单体项目照搬微服务目录层级。
- 过度接口化，导致目录很多但实现很空。

### 14. 最终结论
好的代码组织，应该让开发者做到：
- 通过目录快速定位业务模块。
- 通过文件名快速定位业务动作。
- 通过层次快速判断依赖方向。
- 通过 `pkg` 边界快速判断哪些能力能复用。

单体项目最重要的，不是目录看起来多高级，而是：

**新功能能快速接入，旧功能能快速定位，跨模块修改不会轻易失控。**

## 十六、测试策略

### 推荐测试金字塔
#### 1. 单元测试，70%~80%
重点测试：
- service 业务规则。
- 校验逻辑。
- 权限判断。
- 状态流转。
- 错误码映射。

#### 2. 集成测试，15%~25%
重点测试：
- repository + MySQL。
- repository + Redis。
- 关键关系查询 + Neo4j。
- 少量 HTTP 黑盒测试。

#### 3. 端到端 / 冒烟测试，5%
保留最关键的 3~8 条链路：
- 健康检查。
- 登录 / 注册。
- 核心业务主链路。
- 一个权限拒绝场景。
- 一个事务回滚场景。

### mock 策略
推荐优先使用**手写 fake/stub**，而不是一开始就大量 gomock。

优点：
- 阅读成本低。
- 改接口时噪音小。
- 更适合中小项目。

### 重点补强项
新单体项目必须比微服务时代更重视：
- repository 的真实存储集成测试。
- 事务行为测试。
- 缓存一致性测试。

因为单体的主风险通常就在这些地方。

## 十五、可观测性

低数据量项目不代表不需要可观测性。

建议至少具备：
- 请求日志。
- panic 日志。
- 关键慢查询日志。
- Redis 慢操作或异常日志。
- 健康检查接口。
- 构建版本 / 启动配置摘要。

如果有余力，再增加：
- Prometheus metrics。
- OpenTelemetry tracing。
- pprof。

建议策略：
- 第一阶段先保证日志质量。
- 第二阶段再上 metrics。
- tracing 可按需要接入。

---

## 十六、安全与风控基础

即便用户量只有 200，也不能忽略基本安全面。

至少做到：
- 配置中不硬编码密钥。
- 密码必须安全哈希。
- JWT/Token 有过期与撤销策略。
- 验证码接口有限流。
- 登录接口有限流。
- Recovery 日志脱敏。
- 错误响应不暴露内部细节。
- CORS 策略明确。
- 管理接口与普通接口鉴权分层。

## 十七、我建议你继承的经验

1. 统一上下文元信息模型。
2. 统一结构化日志。
3. 统一错误码与统一响应。
4. 手动依赖注入。
5. repository 层错误翻译。
6. Redis key 与 TTL 集中治理。
7. 优雅停机。
8. 以 service 为测试主战场。

---

## 十八、我建议你不要照搬的内容

1. 不要照搬微服务代理式 service。
2. 不要照搬 protobuf 转换层。
3. 不要照搬过细接口拆分。
4. 不要照搬熔断、补偿队列、复杂异步框架。
5. 不要照搬“业务错误统一 HTTP 200”而不重新评估。
6. 不要为了未来可能拆服务，就把当前单体设计得非常绕。

## 十九、推荐初始化顺序

推荐应用启动顺序：

1. 加载配置。
2. 初始化日志。
3. 初始化 MySQL。
4. 初始化 Neo4j。
5. 初始化 Redis。
6. 初始化 repository。
7. 初始化 service。
8. 初始化 handler。
9. 初始化 router。
10. 初始化 HTTP Server。
11. 注册优雅停机钩子。
12. 启动服务。

## 二十、最终架构结论

对于你的下一个项目，我的推荐不是“复杂但先进”，而是：

**以单体最佳实践为核心，保留清晰边界与扎实工程能力，用最少的抽象换取最高的可维护性。**

- `config` 模板。
- `service/repository` 模板。
- `gorm + redis + neo4j` 初始化模板。
